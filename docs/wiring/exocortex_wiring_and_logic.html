Port mapping

A0 listens on port 80 internally. Docker maps it to a random high port on the host on every container start. The mapped port changes on every docker restart. Operators (and the browser) must check the current port:

docker port exocortex_v16 | grep '80/tcp'
# Example: 0.0.0.0:32793->80/tcp

docker port exocortex_v17 | grep '80/tcp'
# Example: 0.0.0.0:32794->80/tcp

Inside the container, idle_watch.py hardcodes _A0_PORT = 80 for the daemon's HTTP calls to A0's API — the daemon is in the same network namespace and addresses A0 by its internal port, not the host mapping. (This was a real bug earlier in May where get_web_ui_port() returned 5000 from the daemon's argv context instead of A0's 80 — fixed by hardcoding.)

02Extension Load Path Resolution #

A0 resolves extensions through subagents.get_paths(agent, "extensions/python", <hook>). The extensions/python subpath is hardcoded in helpers/extension.py. This is the single most-bitten fragile seam in the project: files placed at any path that doesn't include the python/ segment are invisible to A0 and will silently fail to load — the file exists on disk, syntax-checks fine, but its execute() is never called.

Wiring — The Four Paths

For a given hook (e.g. tool_execute_after) and extension file (e.g. _70_idle_trigger.py), there are four paths the file can live at inside the container. Only the first two (under extensions/python/) are reachable by A0's loader. The other two are residue from earlier naming schemes or operator typos.

PriorityPathLoaded?Purpose
1 /a0/usr/agents/agent0/extensions/python/<hook>/ yes Profile path — canonical home for Exocortex extensions. Wins dedup-by-filename.
2 /a0/usr/plugins/exocortex/extensions/python/<hook>/ yes Plugin path — also loaded. Same filename as profile path → profile wins. Different filename → both load.
3 /a0/python/extensions/<hook>/ yes (default) A0 core default. Loaded last in priority. Per-stem dedup means profile path overrides if same filename exists.
— /a0/usr/agents/agent0/extensions/<hook>/ (no python/) no Common typo target. Invisible to get_paths. Tonight's mis-deploy landed here.
— /a0/usr/Exocortex/extensions/<hook>/ no Legacy location from pre-DEC-030 layout. Stray copies sometimes linger here.

What this looks like when it bites: You edit a file, docker cp it to the container, see "OK no error," check the on-disk md5 against your local copy — they match. You restart the agent or send a test message. Behavior is unchanged. You add a debug print to execute(). It never appears in logs. You start questioning whether the hook fires at all. The fix appears correct, the deploy appears successful, and execution appears absent. The cause: your docker cp target was missing python/, the file landed at an invisible path, and a different (stale) copy at the canonical path is what A0 actually loaded.

Reload behavior — when does new code take effect?

ChangeWhat triggers reloadWhat does NOT
Edit extension .py Container restart (full docker restart) OR supervisorctl restart run_ui Clearing pycache alone. New file at correct path alone. Sending a message.
Edit prompt .md (e.g. fw.msg_repeat.md) Next read by A0 — usually immediate —
Edit config .json Depends — most are read per turn; config.json sections vary —
Edit daemon (idle_watch.py) supervisorctl restart idle_watch run_ui restart. Container restart works too but heavier.
Why pycache clear isn't enough: A0 caches loaded extension classes in memory (_CLASSES_CACHE_AREA in helpers/extension.py). Pycache clear forces a cold import on next reference, but only if a reference happens. The cache only invalidates on Python process restart. supervisorctl restart run_ui kills and respawns the Python process; that's what flushes the cache.

Mitigations

  • Always prefer install scripts over manual docker cp. install_idle_engine.sh et al. have the correct EXT_DEST path baked in.
  • If you must docker cp manually: the destination MUST contain extensions/python/<hook>/. Verify with md5sum from inside the container against your local copy after every deploy.
  • When debugging "fix doesn't take effect": run find /a0 -name <file> -not -path "*/__pycache__/*" | xargs md5sum — if multiple md5s appear, you have stale copies misleading you.
  • The shared lib/install_common.sh refactor (queued separately) will move the post-deploy md5 verification into every install script automatically.

03Hook Pipeline #

Agent Zero fires 13 hooks at fixed points during the agent's loop. Extensions within each hook run in numeric prefix order (lower first). Inserting a new extension at an existing number silently reorders others — always check for prefix collisions before adding. The most load-bearing thing to know about this pipeline: before_main_llm_call fires after prepare_prompt() assembles the prompt, so any extension that writes to loop_data.history_output in that hook is wasting its work. Real injectors must use message_loop_prompts_after.

04Shared State Map #

The implicit contract layer. State written by one component, read by another, with no compile-time enforcement that the writer and reader agree on the key, the type, or the lifecycle. This section catalogs every state surface in the stack: agent.data dict signals, agent attributes (_-prefixed), loop_data.extras_persistent for per-iteration handoff, supervisor sub-state, file-backed persistent state, and cross-file string constants. The most fragile seams in the project (§13 #1, #2, #3) all live here. When a state key changes, both sides need to change together — and there's no test that fails when they don't.

The rule to internalize: Adding a new state key means adding it to this section's tables before adding the reader. If the reader is added without the table entry, the next builder won't know the contract exists. The tables are the contract.

Wiring — Five State Surfaces

The stack uses five distinct state surfaces, each with different lifecycle, scope, and access pattern. Knowing which surface a piece of state lives on determines who can read it, when it expires, and what breaks if the contract drifts.

SurfaceAccess patternLifecycleScope
agent.data dict agent.set_data(key, val) / agent.get_data(key) Persists across turns in the same chat context Per-agent-instance (per chat)
Agent attributes (_-prefixed) setattr(self.agent, "_x", val) / getattr(agent, "_x", default) Persists across turns in the same chat context Per-agent-instance (per chat)
loop_data.extras_persistent Dict access: loop_data.extras_persistent[key] = val Per-iteration of the agent's loop — typically read by A0's prompt template same turn Per-turn
Supervisor sub-state Inside the _supervisor_state dict (which is itself an agent attribute) Per-agent-instance, with internal turn counter Supervisor only — should not be touched by other extensions
File-backed state Read/write to /a0/usr/Exocortex/... JSON/JSONL files Persists across container restarts Cross-context (all chats can see it)

Two patterns matter for understanding which surface to use:

  • Attribute vs data dict: Both persist per-chat. The convention in this codebase is that attributes are for typed objects (the BST store dict, the PACE plan dict, the reasoning state dict, the working memory buffer) and the data dict is for boolean flags and signaling (_pace_advance_tier, _pace_new_task, _action_gate_active). The choice isn't strictly enforced but the pattern is consistent. See §13 seam #3 — confusion between the two access patterns has caused real bugs.
  • extras_persistent vs history_output: Both reach A0's prompt assembly. extras_persistent writes go to template placeholders ({memories}, {solutions}, etc.). history_output writes mutate the assembled history list directly. Both must be written in message_loop_prompts_after to actually reach the LLM call — writes in before_main_llm_call are silently discarded (§13 seam #7).

Where two writers can interact on the same surface. Most are intentional; some are bugs waiting to happen.

def _select_cycle_type(state, config):
    maintain_count = state.get("consecutive_maintain_count", 0)
    build_count    = state.get("build_cycle_count", 0)
    maintain_threshold = config.get("maintain_cooldown_threshold", 3)

Current Bugs — Live Status

🔴 Heartbeat freeze

Trigger: Any idle cycle, after its first tool call.

Mechanism: _last_user_msg_is_real() walks history backwards for the most recent non-AI message. It currently stops at the first non-AI message — which after the first tool call is always a tool result (dict with tool_name key) or a system warning (dict with system_warning key). Neither contains the idle activation sentinel. Returns True (="real user"), so the heartbeat branch is skipped.

Fix: Only stop at messages with a user_message key (the format fw.user_message.md produces). Skip tool results, system warnings, and other injections.

Deployment status: Committed in 69b725d. Mis-deployed to /a0/usr/agents/agent0/extensions/tool_execute_after/ (missing the python/ segment). Active path still has the buggy version.

Resolution path: Run scripts/install_idle_engine.sh + supervisorctl restart run_ui on both containers.

🔴 Overlap (no lifecycle ownership)

Trigger: Any stale-detect, or any cycle that runs past min_gap without completing.

Mechanism: Daemon's _fire_fresh_cycle() POSTs to /api/api_message in a daemon thread that joins with a 3-second timeout. The response (which contains context_id) is never read — A0 holds the connection open until the task completes (minutes). The daemon has no record of what context it spawned. Stale-clear flips the in-memory flag but the A0 context object lives on in run_ui's process, still calling the LLM.

Fix surface (proposed, awaiting Opus spec):

  1. Capture context_id by polling /a0/usr/chats/ for new directories after fire (filesystem-visible immediately).
  2. Store cycle_context_id in engine_state.json.
  3. Before any fire AND on stale-detect: POST /api/api_reset_chat for the stored id.
  4. Make cycle_active a derived property of "context_id non-null AND chat directory exists with fresh mtime."

Resolution path: Briefing to Opus → spec → implementation.

Opus's prediction: "My prediction: [overlap] disappears [when the heartbeat fix actually deploys]. The overlap was caused by premature stale detection, which was caused by the heartbeat not updating, which was caused by the fix being at the wrong path. One root cause, one fix, deployed correctly this time."

This is testable. After the redeploy, the next idle cycle that runs to natural completion should show: heartbeat updates throughout, no stale-clear during the run, single context active at any time. If overlap persists, the lifecycle-ownership work is genuinely needed. If it doesn't, the ownership work becomes defense-in-depth rather than load-bearing.

06Supervisor Loop #

The supervisor is the XO. It runs in message_loop_end after each agent loop iteration and watches for anomalies — stalls, loops, cascading failures, context exhaustion, output stagnation, completion stalls. When it detects one, it injects steering via hist_add_warning(). The escalation is graduated: Tier 1 is silent monitoring (since SFX-001, 2026-04-15), Tier 2 is context surgery (removes loop messages, injects diagnostic), Tier 3 is circuit breaker (forces response), Tier 4 is anti-pattern capture (stores the loop-and-recovery pair to procedural memory for cross-session prevention). The supervisor reads from many state surfaces (§04) and writes _supervisor_state, _loop_active, and history injections.

Design lineage: The supervisor's behavior was specified across specs/LOOP_FEEDBACK_CASCADE_DESIGN_NOTE.md (Session 049 — Tiers 1-3), LOOP_FEEDBACK_CASCADE_ADDENDUM.md (Session 055 — Tier 4), and SUPERVISOR_LOOP_SPEC_L3.md. SFX-001 (2026-04-15) silenced Tier 1 after evidence that injecting "LOOP DETECTED" into a context heavy with failed attempts produces meta-loops — the agent reads the prescription, tries the prescribed action, that also looks repetitive, the detector fires again. Tier 2's context surgery is now the first substantive intervention.

Tier 2 Context Surgery — How It Works

The mechanism that makes the loop cascade architecturally distinct from a simple warning injector. The loop messages aren't ignored — they're removed from the current history topic. The model's next inference sees its pre-loop progress plus a single diagnostic summary, not 4-7 identical failure attempts reinforcing the pattern.

# In _execute_tier2():
#   1. Locate the "incision point" — turn before the loop began
#   2. Truncate history topic from incision_idx forward
#   3. Build summary: failing tool + suggested alternative + anti-action
#   4. Insert summary as a system warning at incision_idx
#   5. agent.context.log.log() the surgery for audit trail

# Result: model continues from pre-loop progress with a clear note
# about what failed, what alternative to try, and what not to retry.

Change 1F (Session 116 territory) added false recovery detection: before performing surgery, check whether a previous surgery has already been attempted on this exact tool and is failing again. If so, escalate to Tier 3 directly rather than repeating a Tier 2 that didn't hold. This is the first time the supervisor maintained a model of its own action history rather than just current state.

Cooldown System

Same-type anomalies don't re-inject too quickly. Each anomaly type has a cooldown counter (turns since last fire of that type). DEFAULT_COOLDOWN = 3 turns. Emergency PACE is exempt from cooldown. Tier 3 has its own T3_REPEAT_COOLDOWN between consecutive fires.

Cooldowns live in _supervisor_state["cooldowns"] as {anomaly_type: turn_number}. _cooldown_ok(state, anomaly_type) returns True iff state["turn"] - state["cooldowns"].get(anomaly_type, 0) ≥ DEFAULT_COOLDOWN.

Phase 4 — LLM-Driven Adjudication

The only path in the supervisor that makes an LLM call. Phase 4 fires when:

  • No higher-tier intervention has already fired this turn
  • _should_trigger_phase4() returns True (specific multi-signal trigger)
  • cooldown_ok(ANOMALY_PHASE4) is True

It builds a compressed context (recent failures, BST domain, effective domain, prior state), then calls an LLM with a 10-second timeout. Returns one of three actions:

ActionEffect
ESCALATEApply tier escalation (set _pace_advance_tier or move tier state)
DEESCALATEApply tier deescalation (relax intervention)
HOLDDefault. Any failure (LLM unavailable, timeout, malformed response) → HOLD.

This is the supervisor's only probabilistic component. Everything else is deterministic threshold logic. Phase 4 is an opt-in LLM judgment layer that operates only when the deterministic system isn't sure.

07BST & Compound Classification #

The Belief State Tracker is Layer 1 of the 12-layer stack — the deterministic preprocessing step that classifies user intent before the model sees it. Lives in extensions/before_main_llm_call/_11_belief_state_tracker.py. Currently v3.8 (phrase-signal architecture). Produces a compound classification (primary domain + secondary domain + complexity) that drives enrichment template injection, action gate calibration, memory recall scoping, supervisor threshold lookups, and supervisor PACE escalation. The BST is the most-read component in the stack — over a dozen extensions depend on its output (full reader list in §04 Surface 2, _bst_store).

The Two Access Patterns (and the bug they caused)

The most consequential BST seam — confused access patterns to the nested classification — caused a real production bug. It's worth explicit treatment because the fix is established and the trap remains for new code.

The trap: The BST writes its primary classification to agent._bst_store["__bst_belief_state__"]["domain"] — two levels deep inside the store dict. Code that reads bst_store.get("domain", "") (one level too shallow) gets an empty string and falls back to "default" — silently, no error. The supervisor's _12_proactive_supervisor had this exact bug at line 191 until 2026-05-14: bst_domain was always empty string, so all PACE threshold lookups used the default tier instead of the model-specific one.

The correct read patterns:

# Wrong — returns empty string silently
bst_domain = bst_store.get("domain", "")

# Right — reads the nested key
bst_store = getattr(self.agent, "_bst_store", {}) or {}
belief    = bst_store.get("__bst_belief_state__")
if belief and hasattr(belief, "primary_domain"):
    bst_domain = str(belief.primary_domain)
elif isinstance(belief, dict):
    bst_domain = str(belief.get("domain", "unknown"))
else:
    bst_domain = "unknown"

# Also right — read from extras_persistent if message_loop_prompts_after
domain = loop_data.extras_persistent.get("_bst_domain", "")

Note also seam #3: always use getattr(agent, "_bst_store", {}), never agent.get_data("_bst_store"). The first works; the second returns None because the BST writes to the attribute surface, not the data dict surface.

Compound Classification

The BST doesn't just emit a single domain. It emits a compound signature — primary domain plus optional secondary domain plus complexity. The compound enables downstream components to make finer distinctions than a flat domain label would allow.

// Example _bst_store contents:
{
  "__bst_belief_state__": {
    "domain": "investigation",
    "primary_domain": "investigation",
    "secondary_domain": "analysis",
    "confidence": 0.84,
    "slots": { ... }
  },
  "_compound_sig": "investigation+analysis",
  "_compound_turns": 3,        // momentum: 3 consecutive turns in this signature

// And in extras_persistent (same turn):
loop_data.extras_persistent["_bst_domain"]    = "investigation"
loop_data.extras_persistent["_bst_compound"]  = {
  "primary":    "investigation",
  "secondary":  "analysis",
  "complexity": "complex"
}

The compound signature drives:

  • Enrichment template selection — different domain combinations select different scaffolding (e.g. investigation+analysis gets epistemic-integrity hints; config_edit gets meta-reasoning gate parameter checks)
  • Tool registry filtering — _16_tool_registry reads _bst_compound.secondary.domain to surface tools relevant to both primary and secondary domains
  • Supervisor model overrides — domain-specific tier thresholds applied via model profile lookup
  • Memory recall scoping — _56_memory_enhancement reads the domain to weight relevance signals

Momentum tracking

The _compound_turns counter increments when consecutive turns share the same compound signature. The agent's domain "momentum" is information beyond the current classification — it tells downstream components whether the agent has been stable in one domain for a while (high confidence) or just shifted (low confidence, treat domain hint as provisional).

Momentum was directly implicated in specs/LOOP_FEEDBACK_CASCADE_DESIGN_NOTE.md's motivating incident: the 14B model looped for 43 turns with momentum locked at config_edit+prompt_engineering (the wrong domain for the task). 08Memory Subsystem #

Two FAISS stores plus an ontology area plus a file-based procedural memory. Memories are written by the agent via the memory_save tool and by the selective memorizer (Layer 10); they're recalled via the relevance filter and enhancement extensions in message_loop_prompts_after (Layer 11). The reasoning state and PACE plan subsystems are designed to give the model visible memory of its own reasoning across turns — what it already tried, what worked, what the current strategy is. They were silently inert until 2026-05-30 — this paragraph documents the historical broken state, now RESOLVED (see Status below): the generator side wrote to agent._reasoning_state and agent._pace_plan correctly, but the injection side fired in before_main_llm_call where loop_data.history_output writes are discarded (seam #7), and no consumer in message_loop_prompts_after read either attribute. Per enable_thinking_correction_20260516.md, the model is now configured to think freely (enable_thinking: true at the request level; --reasoning off at the server only suppresses empty template-tag injection). from agent import Agent, LoopData
from helpers.extension import Extension

REASONING_KEY = "_reasoning_state"

class ReasoningStateInjector(Extension):
    """message_loop_prompts_after: inject compressed reasoning state into context."""

            if self.agent.get_data(Agent.DATA_NAME_SUPERIOR) is not None:
                return  # subordinate context — skip (DEC-028)

            if not state:
                return

            if not block:
                return
            user_msg = _get_last_user_message(loop_data.history_output)
            if user_msg:
                existing = user_msg.get("content", "")
                user_msg["content"] = block + "\n\n" + str(existing)

Seam #13 — Heartbeat freeze in idle cycles ACTIVE

Where it lives: _70_idle_trigger.py in tool_execute_after, function _last_user_msg_is_real().

What goes wrong: The function walks agent.history.output() backwards looking for the most recent non-AI message and asks "is this an idle activation or a real user?" It stops at the first non-AI message it finds. After the first tool call in a cycle, the most recent non-AI message is always a tool result (dict with tool_name key) or a system warning (dict with system_warning key from fw.warning.md). Neither contains the idle-activation sentinel. The function returns True ("this is a real user"), the heartbeat update branch is skipped, and the heartbeat freezes at the value set when the cycle first started.

How to detect:

  • Read engine_state.json during a running idle cycle
  • Compare cycle_heartbeat to last_cycle_start — if equal (or close), heartbeat has not been updating
  • Symptom in logs: [IDLE-WATCH] Stale cycle detected firing on cycles that are clearly still doing work

Why it's actively biting: Every idle cycle reaches the 20-minute stale-detect threshold. The daemon clears cycle_active=false and fires a new cycle on the next poll, even though the original cycle is genuinely healthy and still working. This is the upstream cause of seam #14's user-visible "multiple cycles at once" — overlap fires on every cycle rather than only on genuinely-stuck ones.

Fix: Committed as 69b725d. Function rewritten to skip tool results and warning injections — only stops at messages with a user_message key (the canonical format from fw.user_message.md). Deployed to /a0/usr/agents/agent0/extensions/tool_execute_after/_70_idle_trigger.py (no python/ segment) — wrong path. Active path still has the buggy version.

Resolution path: Re-run scripts/install_idle_engine.sh + supervisorctl restart run_ui on both containers. Verify post-deploy md5 matches the repo. After deploy, observe one cycle to completion to confirm heartbeat updates during tool calls and stale-detect does not fire prematurely.

Seam #14 — Idle context lifecycle not owned ACTIVE

Where it lives: idle_watch.py functions _fire_fresh_cycle() and _atomic_check_and_fire().

What goes wrong: _fire_fresh_cycle() POSTs to /api/api_message in a daemon thread that joins with a 3-second timeout. A0 holds the connection open until the cycle's task.result() completes — minutes. The HTTP response (which contains the new context_id) is never read by the daemon. The daemon has no record of what A0 context it spawned. When stale-detect fires later, it flips cycle_active=false but cannot call /api/api_reset_chat for the specific context because it doesn't know the id. The A0 context object remains alive in run_ui's process, still making LLM calls. Daemon then fires a new cycle on the next poll, creating a second concurrent context.

How to detect:

  • List /a0/usr/chats/ and find chat directories named "Autonomous Work Cycle" with overlapping creation timestamps
  • Check chat.json for each — if streaming_agent is non-null and history is recent, the context is still active
  • From outside: watch GPU utilization or LM Studio request log for sustained activity after a stale-detect log entry

Why it's hard to fix correctly: The natural place to record context_id is from the HTTP response — but the daemon can't wait minutes for that response. Alternatives: poll /a0/usr/chats/ for new directory entries after firing (filesystem-visible immediately on context creation); or add an asynchronous endpoint to A0 that returns the context_id immediately after queueing the task. Option 1 is buildable without modifying A0.

Proposed fix surface (awaiting Opus spec):

  1. Snapshot set(os.listdir('/a0/usr/chats/')) before firing
  2. Fire activation (existing http.client thread)
  3. Poll /a0/usr/chats/ for the new directory (1-5 second window)
  4. Write cycle_context_id to engine_state.json
  5. Before any subsequent fire, AND on stale-detect: POST /api/api_reset_chat with the stored context_id; clear the field on success
  6. Promote cycle_active to a derived property: True iff cycle_context_id non-null AND chat directory still exists with fresh mtime

Resolution path: Briefing to Opus pending — but possibly downgraded. Opus's hypothesis (recorded in §05) is that this seam's user-visible symptom (overlap) may largely disappear once seam #13 (heartbeat freeze) is fixed. If overlap stops happening, the lifecycle-ownership work becomes defense-in-depth rather than load-bearing. We'll know after observing one healthy post-heartbeat-fix cycle.

The DEC-026 shared library refactor — proposed

Target: scripts/lib/install_common.sh, sourced at the top of every install_*.sh. Functions extracted:

  • _exec() — MSYS_NO_PATHCONV=1 docker exec wrapper for Windows Git Bash path-translation immunity.
  • get_containers() — returns the active container list (exocortex_v16, exocortex_v17), supports CONTAINER_NAME env override.

  • install_file_if_missing() — same but skips if destination already exists. For user-edit-survivable files like interests.md.
  • clear_pycache() — standardized pycache wipe for a given module.
  • find_orphans() — DEC-026 scan. find /a0 -name <file> -not -path "*/__pycache__/*" + md5 each result + warn on any that don't match the canonical version.
  • print_restart_hint() — emits the supervisorctl restart run_ui command the caller needs to run after extension changes.

Per-deployment gates (DEC-031, from playbook)

Standing rule even before the shared lib lands: every extension deploy must clear all five gates in order. Skipping any of 4-5 because 1-3 looked clean is the failure mode that produced tonight's incident.

  1. Syntax check passes: python3 -m py_compile <file>.py
  2. File deployed: docker cp exit 0
  3. Pycache cleared: all .cpython-*.pyc files for this module removed
  4. Symbol verified in container: docker exec md5sum matches local md5 (or grep for a unique string in the deployed file)
  5. Log tag appears: send a test trigger, check docker logs --since=60s | grep '[TAG]'

FAISS consistency

index.faiss and index.pkl must be captured as a consistent pair — a torn copy looks fine and restores broken, which is worse than no backup at all. The index.faiss.sha256 sidecar is verified in-container before capture; a mismatch is recorded as DEGRADED in the run manifest rather than silently accepted. (Related: Memory.index is a class-level RAM cache — the on-disk pair is only rewritten on _save_db(), so a capture during a write window is the risk this check exists for.)

MCP health diagnostic

_02_mcp_health.py (before_main_llm_call) reports live MCP connection state and raises a CRITICAL line when a required server is missing or down. It exists because Vek ran 2026-08-03 → 08-12 with no exocortex-memory server at all while his prompts told him to ground every BUILD cycle in it — cycles reported completed, journals looked normal, nine days of research ran ungrounded, and nothing in the stack reported MCP state.

It must run inside A0's process: a separate process gets a fresh MCPConfig singleton that reports zero servers regardless of truth, and /api/mcp_servers_status can exceed a request timeout. Both failed to diagnose the outage. On its first live fire it also caught its own false positive — A0 normalizes server names hyphen→underscore (deep-wiki → deep_wiki), so a raw string compare reported a server as simultaneously connected and missing.
