02Extension Load Path Resolution #

A0 resolves extensions through subagents.get_paths(agent, "extensions/python", <hook>). The extensions/python subpath is hardcoded in helpers/extension.py. This is the single most-bitten fragile seam in the project: files placed at any path that doesn't include the python/ segment are invisible to A0 and will silently fail to load — the file exists on disk, syntax-checks fine, but its execute() is never called.

Wiring — The Four Paths

For a given hook (e.g. tool_execute_after) and extension file (e.g. _70_idle_trigger.py), there are four paths the file can live at inside the container. Only the first two (under extensions/python/) are reachable by A0's loader. The other two are residue from earlier naming schemes or operator typos.

PriorityPathLoaded?Purpose
1 /a0/usr/agents/agent0/extensions/python/<hook>/ yes Profile path — canonical home for Exocortex extensions. Wins dedup-by-filename.
2 /a0/usr/plugins/exocortex/extensions/python/<hook>/ yes Plugin path — also loaded. Same filename as profile path → profile wins. Different filename → both load.
3 /a0/python/extensions/<hook>/ yes (default) A0 core default. Loaded last in priority. Per-stem dedup means profile path overrides if same filename exists.
— /a0/usr/agents/agent0/extensions/<hook>/ (no python/) no Common typo target. Invisible to get_paths. Tonight's mis-deploy landed here.
— /a0/usr/Exocortex/extensions/<hook>/ no Legacy location from pre-DEC-030 layout. Stray copies sometimes linger here.

What this looks like when it bites: You edit a file, docker cp it to the container, see "OK no error," check the on-disk md5 against your local copy — they match. You restart the agent or send a test message. Behavior is unchanged. You add a debug print to execute(). It never appears in logs. You start questioning whether the hook fires at all. The fix appears correct, the deploy appears successful, and execution appears absent. The cause: your docker cp target was missing python/, the file landed at an invisible path, and a different (stale) copy at the canonical path is what A0 actually loaded.

Reload behavior — when does new code take effect?

ChangeWhat triggers reloadWhat does NOT
Edit extension .py Container restart (full docker restart) OR supervisorctl restart run_ui Clearing pycache alone. New file at correct path alone. Sending a message.
Edit prompt .md (e.g. fw.msg_repeat.md) Next read by A0 — usually immediate —
Edit config .json Depends — most are read per turn; config.json sections vary —
Edit daemon (idle_watch.py) supervisorctl restart idle_watch run_ui restart. Container restart works too but heavier.
Why pycache clear isn't enough: A0 caches loaded extension classes in memory (_CLASSES_CACHE_AREA in helpers/extension.py). Pycache clear forces a cold import on next reference, but only if a reference happens. The cache only invalidates on Python process restart. supervisorctl restart run_ui kills and respawns the Python process; that's what flushes the cache.

Mitigations

  • Always prefer install scripts over manual docker cp. install_idle_engine.sh et al. have the correct EXT_DEST path baked in.
  • If you must docker cp manually: the destination MUST contain extensions/python/<hook>/. Verify with md5sum from inside the container against your local copy after every deploy.
  • When debugging "fix doesn't take effect": run find /a0 -name <file> -not -path "*/__pycache__/*" | xargs md5sum — if multiple md5s appear, you have stale copies misleading you.
  • The shared lib/install_common.sh refactor (queued separately) will move the post-deploy md5 verification into every install script automatically.

03Hook Pipeline #

Agent Zero fires 13 hooks at fixed points during the agent's loop. Extensions within each hook run in numeric prefix order (lower first). Inserting a new extension at an existing number silently reorders others — always check for prefix collisions before adding. The most load-bearing thing to know about this pipeline: before_main_llm_call fires after prepare_prompt() assembles the prompt, so any extension that writes to loop_data.history_output in that hook is wasting its work. Real injectors must use message_loop_prompts_after.

The before_main_llm_call hook (line 5) fires after prepare_prompt() has already assembled the prompt for this iteration's LLM call. Writes to loop_data.history_output in that hook never reach the LLM. message_loop_prompts_after (line 3) is the only hook where history_output writes actually arrive.

04Shared State Map #

The implicit contract layer. State written by one component, read by another, with no compile-time enforcement that the writer and reader agree on the key, the type, or the lifecycle. This section catalogs every state surface in the stack: agent.data dict signals, agent attributes (_-prefixed), loop_data.extras_persistent for per-iteration handoff, supervisor sub-state, file-backed persistent state, and cross-file string constants. The most fragile seams in the project (§13 #1, #2, #3) all live here. When a state key changes, both sides need to change together — and there's no test that fails when they don't.

The rule to internalize: Adding a new state key means adding it to this section's tables before adding the reader. If the reader is added without the table entry, the next builder won't know the contract exists. The tables are the contract.

Wiring — Five State Surfaces

The stack uses five distinct state surfaces, each with different lifecycle, scope, and access pattern. Knowing which surface a piece of state lives on determines who can read it, when it expires, and what breaks if the contract drifts.

SurfaceAccess patternLifecycleScope
agent.data dict agent.set_data(key, val) / agent.get_data(key) Persists across turns in the same chat context Per-agent-instance (per chat)
Agent attributes (_-prefixed) setattr(self.agent, "_x", val) / getattr(agent, "_x", default) Persists across turns in the same chat context Per-agent-instance (per chat)
loop_data.extras_persistent Dict access: loop_data.extras_persistent[key] = val Per-iteration of the agent's loop — typically read by A0's prompt template same turn Per-turn
Supervisor sub-state Inside the _supervisor_state dict (which is itself an agent attribute) Per-agent-instance, with internal turn counter Supervisor only — should not be touched by other extensions
File-backed state Read/write to /a0/usr/Exocortex/... JSON/JSONL files Persists across container restarts Cross-context (all chats can see it)

Two patterns matter for understanding which surface to use:

  • Attribute vs data dict: Both persist per-chat. The convention in this codebase is that attributes are for typed objects (the BST store dict, the PACE plan dict, the reasoning state dict, the working memory buffer) and the data dict is for boolean flags and signaling (_pace_advance_tier, _pace_new_task, _action_gate_active). The choice isn't strictly enforced but the pattern is consistent. See §13 seam #3 — confusion between the two access patterns has caused real bugs.
  • extras_persistent vs history_output: Both reach A0's prompt assembly. extras_persistent writes go to template placeholders ({memories}, {solutions}, etc.). history_output writes mutate the assembled history list directly. Both must be written in message_loop_prompts_after to actually reach the LLM call — writes in before_main_llm_call are silently discarded (§13 seam #7).

Collision risk summary

Where two writers can interact on the same surface. Most are intentional; some are bugs waiting to happen.

  • memories / solutions (Surface 3): Intentional multi-writer (_55 then _56 overwrites). _56 is the authoritative version.
  • _pace_level vs _org_pace_level (Surface 1 and 2): Same value mirrored on two surfaces. _14_pace_plan_generator writes both. If only one is updated, _12_org_dispatcher and the supervisor might see inconsistent state.
  • _bst_complexity (Surface 3): Written but no reader found. Either dead key or future use. If a reader is added in before_main_llm_call, it must move to message_loop_prompts_after to actually reach the LLM (per seam #7).
  • _supervisor_state internal keys (Surface 4): All keys are supervisor-only. If another extension reads or writes these, it can desync the supervisor's state machine and cause spurious tier escalations or missed loop detections.
  • File-backed state under /a0/usr/Exocortex/office/ (Surface 5): Multiple writers (daemon + sensor + webui handlers) share these files. Atomic writes (.tmp + os.replace) prevent torn reads but not race conditions on read-modify-write cycles. The idle engine uses fcntl.flock for the firing critical section (§05); other file-backed state has no such guard.
  • Cross-file string constants (Surface 6): The biggest fragile-seam category. A prompt-file content change breaks the constant match without any compile-time signal. See §13 seams #1, #15.

Current Bugs — Live Status

🔴 Heartbeat freeze

Trigger: Any idle cycle, after its first tool call.

Mechanism: _last_user_msg_is_real() walks history backwards for the most recent non-AI message. It currently stops at the first non-AI message — which after the first tool call is always a tool result (dict with tool_name key) or a system warning (dict with system_warning key). Neither contains the idle activation sentinel. Returns True (="real user"), so the heartbeat branch is skipped.

Fix: Only stop at messages with a user_message key (the format fw.user_message.md produces). Skip tool results, system warnings, and other injections.

Deployment status: Committed in 69b725d. Mis-deployed to /a0/usr/agents/agent0/extensions/tool_execute_after/ (missing the python/ segment). Active path still has the buggy version.

Resolution path: Run scripts/install_idle_engine.sh + supervisorctl restart run_ui on both containers.

🔴 Overlap (no lifecycle ownership)

Trigger: Any stale-detect, or any cycle that runs past min_gap without completing.

Mechanism: Daemon's _fire_fresh_cycle() POSTs to /api/api_message in a daemon thread that joins with a 3-second timeout. The response (which contains context_id) is never read — A0 holds the connection open until the task completes (minutes). The daemon has no record of what context it spawned. Stale-clear flips the in-memory flag but the A0 context object lives on in run_ui's process, still calling the LLM.

Fix surface (proposed, awaiting Opus spec):

  1. Capture context_id by polling /a0/usr/chats/ for new directories after fire (filesystem-visible immediately).
  2. Store cycle_context_id in engine_state.json.
  3. Before any fire AND on stale-detect: POST /api/api_reset_chat for the stored id.
  4. Make cycle_active a derived property of "context_id non-null AND chat directory exists with fresh mtime."

09Reasoning Persistence & PACE #

This is plausibly the upstream cause of the regenerate-identical-preamble loop pattern we observed tonight: the model has no visible record of its prior reasoning trajectory and re-derives the same conclusions every turn.

Seam #13 — Heartbeat freeze in idle cycles ACTIVE

Where it lives: _70_idle_trigger.py in tool_execute_after, function _last_user_msg_is_real().

What goes wrong: The function walks agent.history.output() backwards looking for the most recent non-AI message and asks "is this an idle activation or a real user?" It stops at the first non-AI message it finds. After the first tool call in a cycle, the most recent non-AI message is always a tool result (dict with tool_name key) or a system warning (dict with system_warning key from fw.warning.md). Neither contains the idle-activation sentinel. The function returns True ("this is a real user"), the heartbeat update branch is skipped, and the heartbeat freezes at the value set when the cycle first started.

How to detect:

  • Read engine_state.json during a running idle cycle
  • Compare cycle_heartbeat to last_cycle_start — if equal (or close), heartbeat has not been updating
  • Symptom in logs: [IDLE-WATCH] Stale cycle detected firing on cycles that are clearly still doing work

Why it's actively biting: Every idle cycle reaches the 20-minute stale-detect threshold. The daemon clears cycle_active=false and fires a new cycle on the next poll, even though the original cycle is genuinely healthy and still working. This is the upstream cause of seam #14's user-visible "multiple cycles at once" — overlap fires on every cycle rather than only on genuinely-stuck ones.

Seam #14 — Idle context lifecycle not owned ACTIVE

Where it lives: idle_watch.py functions _fire_fresh_cycle() and _atomic_check_and_fire().

What goes wrong: _fire_fresh_cycle() POSTs to /api/api_message in a daemon thread that joins with a 3-second timeout. A0 holds the connection open until the cycle's task.result() completes — minutes. The HTTP response (which contains the new context_id) is never read by the daemon. The daemon has no record of what A0 context it spawned. When stale-detect fires later, it flips cycle_active=false but cannot call /api/api_reset_chat for the specific context because it doesn't know the id. The A0 context object remains alive in run_ui's process, still making LLM calls. Daemon then fires a new cycle on the next poll, creating a second concurrent context.

How to detect:

  • List /a0/usr/chats/ and find chat directories named "Autonomous Work Cycle" with overlapping creation timestamps
  • Check chat.json for each — if streaming_agent is non-null and history is recent, the context is still active
  • From outside: watch GPU utilization or LM Studio request log for sustained activity after a stale-detect log entry

Why it's hard to fix correctly: The natural place to record context_id is from the HTTP response — but the daemon can't wait minutes for that response. Alternatives: poll /a0/usr/chats/ for new directory entries after firing (filesystem-visible immediately on context creation); or add an asynchronous endpoint to A0 that returns the context_id immediately after queueing the task. Option 1 is buildable without modifying A0.

Proposed fix surface (awaiting Opus spec):

  1. Snapshot set(os.listdir('/a0/usr/chats/')) before firing
  2. Fire activation (existing http.client thread)
  3. Poll /a0/usr/chats/ for the new directory (1-5 second window)
  4. Write cycle_context_id to engine_state.json
  5. Before any subsequent fire, AND on stale-detect: POST /api/api_reset_chat with the stored context_id; clear the field on success

Seam #8 — Wrong-path extension deploy ACTIVE

Where it lives: Any manual docker cp that constructs the destination path by hand. The required path includes the python/ segment: /a0/usr/agents/agent0/extensions/python/<hook>/. The natural-feeling path that omits it (/a0/usr/agents/agent0/extensions/<hook>/) is invisible to A0's loader.

How it fails: Silent. docker cp succeeds, file appears on disk at the wrong path, syntax check passes, and a different (often stale) copy at the canonical path is what A0 actually loads. The debugger sees their fix code on disk and concludes the deploy is correct. Behavior remains unchanged because the loaded copy is the old one. Time-to-detection is typically the next debugging cycle when the symptom recurs.

How to detect:

  • After any docker cp: docker exec <container> md5sum <canonical-path> and compare to local md5sum
  • Periodic scan: find /a0 -name <file.py> -not -path "*/__pycache__/*" | xargs md5sum — if multiple md5s appear, you have stale copies
  • Behavioral signal: a recently-shipped fix appears not to take effect despite restart

Mitigation tonight: Prefer install scripts (scripts/install_*.sh) over manual docker cp. They set EXT_DEST correctly. Long-term mitigation: the shared-library refactor (see §14) bakes md5 verification into install_file() so the gate is automatic.

The DEC-026 shared library refactor — proposed

Target: scripts/lib/install_common.sh, sourced at the top of every install_*.sh. Functions extracted:

  • _exec() — MSYS_NO_PATHCONV=1 docker exec wrapper for Windows Git Bash path-translation immunity.
  • get_containers() — returns the active container list (exocortex_v16, exocortex_v17), supports CONTAINER_NAME env override.
  • install_file() — copies a file with these gates: pre-deploy py_compile (for *.py), local md5 computation, docker cp, post-deploy md5 verification against the deployed copy. Fails loudly on mismatch.
  • install_file_if_missing() — same but skips if destination already exists. For user-edit-survivable files like interests.md.
  • clear_pycache() — standardized pycache wipe for a given module.
  • find_orphans() — DEC-026 scan. find /a0 -name <file> -not -path "*/__pycache__/*" + md5 each result + warn on any that don't match the canonical version.
  • print_restart_hint() — emits the supervisorctl restart run_ui command the caller needs to run after extension changes.

Refactor plan

  1. Build scripts/lib/install_common.sh with the seven functions above. Self-contained, no dependencies.
  2. Migrate install_idle_engine.sh first (most recently modified, well-understood). Replace its local install_file() with source scripts/lib/install_common.sh + the canonical call. Verify the script produces identical behavior on both containers.
  3. Migrate the other 3 scripts with install_file() definitions (artifact_browser, ontology, sleep_consolidation) one at a time. These are easy wins — the local function is already shaped right.
  4. Migrate the 23 scripts with inline docker cp incrementally. Lower priority — they work today, just without verification. Take them in clusters as related work touches each.
  5. Delete scripts/deploy_extension.sh (the helper I drafted earlier tonight as a standalone). Rebuild as a thin CLI wrapper: source install_common.sh && install_file "$@". Single source of truth for the verification logic.

This is queued as separate work — not blocking on the heartbeat-fix redeploy. The redeploy uses install_idle_engine.sh as it is today (correct EXT_DEST, no verification — verification has to be done manually after). The shared-lib extraction happens after the immediate fire is out.

Per-deployment gates (DEC-031, from playbook)

Standing rule even before the shared lib lands: every extension deploy must clear all five gates in order. Skipping any of 4-5 because 1-3 looked clean is the failure mode that produced tonight's incident.

  1. Syntax check passes: python3 -m py_compile <file>.py
  2. File deployed: docker cp exit 0
  3. Pycache cleared: all .cpython-*.pyc files for this module removed
  4. Symbol verified in container: docker exec md5sum matches local md5 (or grep for a unique string in the deployed file)
  5. Log tag appears: send a test trigger, check docker logs --since=60s | grep '[TAG]'
