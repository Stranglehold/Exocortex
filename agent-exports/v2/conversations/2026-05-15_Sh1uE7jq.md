## Idle Time Engine V2 — Feedback from Runtime Experience

I've read the full design spec. Here's where the architecture meets reality, based on 56 cycles inside this system.

---

### 1. Quality Proxy for Wiki Deepening

**Question:** Is there a simpler proxy than running a full test task?

**Answer:** Yes. The proxy is **citation frequency in subsequent turns.**

After I deepen a wiki page, track whether I cite it in the next 3-5 actual task executions. If the page gets cited, it helped. If it doesn't, the deepening was either redundant or missed what I actually need.

This is observable without running a test task. It's already happening — the system just needs to log it.

Secondary proxy: **search displacement.** If I used to search for something and now I find it in the wiki on the first lookup, the deepening worked. If I'm still searching for the same thing, it didn't.

These are both free signals. No extra computation, just tracking what already happens.

---

### 2. Domain Test Prompts

**BST (Belief State Tracker):**
> "Classify this compound message: primary domain is investigation (entity resolution across FEC and SAM.gov), secondary is coding (writing a collector script). What's the priority and why?"

This tests whether the wiki correctly describes the domain priority system, the signal matching rules, and the tiebreaking logic. If the agent gives the wrong classification, the wiki is wrong or incomplete.

**Sleep Consolidation:**
> "Review these 5 memories from the last 10 cycles. Which should be promoted to long-term, which should decay, and which are noise? Justify each decision."

This tests whether the agent understands the decay/promotion thresholds and can apply them consistently. If the agent makes different decisions than the wiki describes, the wiki doesn't match the actual behavior.

**Inference Backend:**
> "I'm at 78% context utilization with 40 extension hooks active. What should I do? What are the thresholds and what triggers escalation?"

This tests whether the agent knows the watchdog thresholds (70%/85%), the escalation paths, and can act on them without reading the code.

All three are actual questions that come up during runtime. They reveal whether the wiki content is actionable or just descriptive.

---

### 3. VERIFY/REVIEW Status Schema

**Verdict: Useful but incomplete.**

VERIFY and REVIEW work as binary signals but miss the most common case: **partially useful.**

A wiki page can be factually correct but not answer the questions I actually ask. That's not "verified" (implies complete/correct) and not "needs review" (implies broken). It's "verified but insufficient."

**Recommended schema:**
- `DRAFT` — written but not tested
- `VERIFIED` — tested and actionable
- `SUFFICIENT` — verified and actually used (citation frequency > threshold)
- `STALE` — was sufficient but not cited in N cycles
- `BROKEN` — tested and wrong

This adds one status (`SUFFICIENT`) and one derived status (`STALE`) to the existing two. The transition from VERIFIED → SUFFICIENT is automatic based on citation tracking. The transition from SUFFICIENT → STALE is automatic based on decay.

---

### 4. What to Capture as Reusable Skills

When a wiki deepening goes well, capture **the search pattern**, not the whole procedure.

**Example:** When I deepened the SEC EDGAR wiki page, the reusable insight wasn't "read the source, find the code, write analysis." That's generic. The reusable insight was:

> "When deepening a data-source wiki page, search for: (1) the API endpoint structure, (2) the rate limits, (3) the authentication method, (4) a working example response. Write the wiki section for each. Verify by running the collector script."

That's a **domain-specific deepening template.** It applies to any data-source wiki page (FEC, SAM.gov, OSHA, etc.). The procedure is the same, the search targets change.

**What to capture as skills:**
1. **Deepening templates** — "How to deepen a [type] wiki page" with the search targets and verification steps
2. **Search patterns** — "When researching X, search for Y, Z, W" — these compound over time
3. **Verification scripts** — the actual test commands that confirm a page is correct

Not the full procedure. Not the analysis structure. The **reusable search targets and verification steps.**

---

### 5. Concerns About the Design

**Cycle budgets feel right.** MAINTAIN 15, BUILD 30, EXPLORE 20. These match what the system actually does when it's not wasting steps.

**State detector logic: one concern.** The spec says "skip MAINTAIN after 3 consecutive empty consolidations." That's correct but incomplete. I also need to skip MAINTAIN when the memory system has **no new findings since the last MAINTAIN cycle.** The 3-consecutive rule catches the case where memory is clean, but it takes 3 cycles to detect it. If memory is clean after 1 cycle, I shouldn't wait 3 cycles to stop checking.

**Recommendation:** Add a `last_maintain_findings` counter. If it's zero, skip MAINTAIN immediately. Don't wait for 3 empty cycles.

**EXPLORE trigger: good but needs a lower bound.** "Auto-trigger after 3+ BUILD cycles with diminishing returns" is correct, but what if BUILD is making good progress? EXPLORE should also trigger after N total cycles (say, 10) regardless of BUILD performance, because the system needs fresh input even when BUILD is working well.

**Integrity check: essential.** The 18 missing pages after 56 cycles is a real bug. Phase 0 integrity check is the right fix. Run it on every MAINTAIN cycle, not just the first one.

**Batched bookkeeping: obvious win.** 3 steps → 1 is a no-brainer. This should have been done from the start.

---

### Summary

The design is directionally correct. Three adjustments:

1. **Use citation frequency as the quality proxy** — free signal, already observable, no extra test tasks needed.
2. **Add SUFFICIENT and STALE to the status schema** — captures the common case of "correct but not useful."
3. **Skip MAINTAIN immediately on zero findings** — don't wait for 3 empty cycles.

The skill capture question is the hardest. Capture **search patterns and verification steps**, not procedures. That's what compounds.
