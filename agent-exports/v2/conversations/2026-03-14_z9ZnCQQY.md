**Verdict: Extract Patterns (Context Schema Only)**

OpenViking's context representation is **URI-based unified model** treating skills, memory, and resources as first-class citizens with the same addressing scheme. The Python/Rust hybrid makes full integration expensive, but their **context schema design decisions** are worth extracting.

---

## OpenViking Context Architecture

### 1. Unified URI-Based Model

```python
# Everything is a "Context" with URI-based addressing:
viking://memories/{user}/{category}/{id}/memory.md
viking://skills/{skill_name}/skill.md  
viking://resources/{resource_type}/{id}/resource.md
viking://session/{user}/{session_id}/messages.jsonl
```

**Key Design**: Single `Context` class for all types with:
- `uri`: Unique identifier (required)
- `abstract`: Summary/description  
- `meta`: Metadata dict (category, overview, etc.)
- `vectorize`: Vectorization instructions
- `content()`: Returns actual content as string

### 2. Context Categories & Taxonomy

| Category | URI Pattern | Purpose |
|----------|-------------|---------|
| **Memories** | `viking://memories/{user}/{category}/` | Extracted knowledge (6 subcategories) |
| **Skills** | `viking://skills/{name}/skill.md` | Reusable capabilities |
| **Resources** | `viking://resources/{type}/{id}/` | External data sources |
| **Sessions** | `viking://session/{user}/{id}/` | Conversation history |

### 3. Memory Extraction System (6 Categories)

```python
MemoryCategory = {
    PROFILE:      # User identity, always merges (no dedup)
    PREFERENCES:  # User preferences, supports merge
    ENTITIES:     # People/places/things mentioned, supports merge  
    PATTERNS:     # Behavioral patterns, supports merge
    TOOLS:        # Tool usage tracking with stats
    SKILLS:       # Skill usage tracking with stats
}
```

**Memory Lifecycle**: Create → Merge/Delete via LLM-based deduplicator

### 4. Session Architecture

```python
class Session:
    - Messages stored in JSONL (append-friendly)
    - Auto-commit when tokens > threshold (default 8000)
    - Archives old messages to history/archive_{index}/
    - Maintains compression summary per archive
    - Tracks usage records for all contexts/skills used
```

**Session Statistics Tracked**:

- Contexts used (memories, resources, skills)
- Memories extracted

## Key Design Decisions to Extract

### 1. Unified Context Abstraction ✅ Worth Adopting
OpenViking's single `Context` class for all types simplifies the mental model significantly. BST currently has:
- `BeliefState` (domain-based)
- `WorkingMemory` (slot-based) 
- Separate skill/resource handling

**Recommendation**: Consider unifying into a single context type with category metadata.

### 2. URI-Based Addressing ✅ Worth Adopting
The `viking://` scheme provides:
- Clear namespace separation
- Self-documenting paths
- Easy serialization/deserialization
- Natural filesystem mapping

**Recommendation**: Adopt similar URI scheme for BST contexts.

### 3. Tool/Skill Usage Tracking ⚠️ Partially Worth Adopting
OpenViking automatically extracts tool/skill usage into memories with statistics. BST currently requires manual tracking via tool response metadata.

**Recommendation**: Add automatic extraction hook in `tool_response` handler.

### 4. Session Auto-Archival ✅ Worth Adopting
The JSONL-based session storage with auto-commit when tokens exceed threshold is elegant and simple.

**Recommendation**: Consider adopting for long-running sessions.

1. **Python/Rust Hybrid Architecture** ❌ Too complex, language mismatch
2. **VikingFS Filesystem Abstraction** ❌ Over-engineered for BST needs
3. **LLM-Based Deduplicator** ❌ Already have selective memorizer + classifier pipeline
