# Key Design Principles Behind PEP 695 Type Parameter Syntax

## Summary of Main Design Goals:

### 1. **Natural Placement** 
Type parameters are declared directly within the class, function, or type alias statement itself, at "a natural place" rather than requiring separate `Generic[T]` base classes or imported `TypeVar` objects.

```python
def func[T](x: T) -> T  # New syntax
# vs. def func(x): ... with TypeVar imports elsewhere
```

### 2. **Eliminate Runtime/Compile-Time Confusion** 
The old approach created a single runtime instance shared across all type usages, causing confusion about what was happening at compile time versus runtime.

### 3. **Consistency with Other Languages**
Python's syntax now aligns more closely with how other languages (C#, Java, Rust) handle generic type parameters, making it more intuitive for developers familiar with those ecosystems.

### 4. **Cleaner Scoping Rules** 
Type parameters are scoped to the class/function/type-alias where they're declared, eliminating ambiguity about their visibility and lifetime.

### 5. **Simplified Type Alias Syntax**
The PEP also introduces a new `type` statement for declaring type aliases inline with proper generic support:

```python
type MyList[T] = list[T]
```

---

**Bottom line:** PEP 695 aims to make Python's generics feel more natural, less verbose, and consistent with both user expectations and how other modern languages handle the same concepts.
